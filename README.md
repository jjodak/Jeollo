# 절로 Jeollo

> AI 이미지 인식으로 보고, 듣고, 모으는 사찰 문화유산 큐레이션 서비스

절로는 사찰을 단순히 둘러보는 공간이 아니라, 걸음마다 전시가 되는
`지붕 없는 박물관`으로 경험하게 만드는 모바일 서비스 기획 프로젝트입니다.
사용자가 사찰의 문화유산을 카메라로 스캔하면 AI가 대상을 인식하고,
음성/영상 도슨트와 상세 해설, 디지털 스탬프 수집 경험을 제공합니다.

## 문제 정의

불교문화와 전통문화에 대한 2030세대의 관심은 커지고 있지만, 실제 사찰
방문은 문화유산 향유 경험으로 충분히 이어지지 못하고 있습니다.

자체 설문조사 기준, 2030세대 사용자는 사찰 방문 시 다음과 같은 불편을
느꼈습니다.

- 교통편이 좋지 않음
- 무엇을 봐야 할지 모르겠음
- 관련 정보를 찾기 어려움
- 놀거리와 구경거리가 부족함
- 편의시설이 부족함

절로는 이 중 콘텐츠 접근성 문제에 집중합니다. 사찰 안의 건축, 단청,
불상, 탱화, 공예, 의례와 같은 유무형 문화유산을 현장에서 바로 이해하고
수집할 수 있는 참여형 경험으로 전환합니다.

## 핵심 가치

- **발견**: 현재 위치를 기반으로 주변 사찰과 방문 가능한 콘텐츠를 추천합니다.
- **이해**: 문화유산을 카메라로 스캔하면 도슨트 해설을 제공합니다.
- **수집**: 스캔과 청취 경험을 디지털 스탬프로 기록합니다.
- **재방문**: 관심 사찰의 소식, 행사, 프로그램을 구독하고 다시 방문하도록 연결합니다.

## 주요 기능

### 홈

- 위치 기반 사찰 추천
- 금주의 인기 소식 제공
- 추천 블로그 자동 연결
- 사찰 행사 및 템플스테이 정보 노출
- 도슨트 투어 핵심 기능으로 바로 이동

### 스캔

- 문화유산 카메라 스캔
- AI 이미지 인식 기반 문화유산 확인
- 음성/영상 도슨트 재생
- 다른 화면으로 이동해도 하단 PIP 형태로 도슨트 계속 재생
- 도슨트 스크립트 보기
- 문화유산 상세 정보 확인

### 탐색/검색

- 상단 검색을 통한 사찰 및 문화유산 검색
- 문화유산, 사찰, 템플스테이/행사, 테마 투어 카테고리 탐색
- 각 카테고리별 목록 및 상세 정보 제공
- 지도 기반 사찰 위치 표시
- 스탬프 획득 사찰 위치 표시

### 스탬프 도감

- 방문 및 스캔으로 획득한 디지털 스탬프 목록화
- 사찰별 문화유산 발견 현황 표시
- 아직 발견하지 못한 문화유산을 비공개 카드로 보여주어 추가 탐색 유도

## 서비스 흐름

1. 사용자는 홈에서 현재 위치 주변의 사찰과 행사 정보를 확인합니다.
2. 방문한 사찰에서 문화유산을 카메라로 스캔합니다.
3. AI가 문화유산을 인식하고 도슨트 콘텐츠를 재생합니다.
4. 사용자는 스크립트와 상세 정보를 함께 확인합니다.
5. 감상한 문화유산은 디지털 스탬프로 수집됩니다.
6. 사용자는 탐색 화면과 지도에서 다른 사찰, 행사, 테마 투어를 이어서 발견합니다.

## 차별점

기존의 사찰 정보 서비스가 검색과 안내에 머무른다면, 절로는 현장 감상,
도슨트 해설, 수집형 경험을 하나의 흐름으로 연결합니다.

- 사찰의 유형유산과 무형유산을 함께 다루는 현장형 큐레이션
- 이미지 인식 기반의 즉시 해설 경험
- 스탬프 수집을 통한 게임화된 탐방 동기
- 관심 사찰 구독을 통한 행사 참여 및 재방문 유도
- 전통문화포털, 국가유산청 등 기존 아카이브와 연계 가능한 콘텐츠 구조

## 비즈니스 모델

절로는 2030세대 비종교인 및 불교문화 관심층을 B2C 사용자로, 협력 사찰과
문화유산 현장을 B2B 파트너로 연결하는 양면 플랫폼을 지향합니다.

- B2C: 도슨트, 추천 콘텐츠, 스탬프 수집, 사찰 소식 구독
- B2B: 협력 사찰의 행사 및 체험 프로그램 홍보
- 수익원: 광고 노출, 알림/홍보 계약, 유료 도슨트 또는 제휴 콘텐츠 확장
- 초기 목표: 가입자 3만 명
- 유효 시장: 2030세대 불교문화 관심층 30~40만 명
- 전체 잠재 시장: 국내 불교문화 관심층 80~90만 명

## 기대 효과

- 사찰 방문자가 문화유산을 더 깊이 이해하도록 돕는 상시 도슨트 경험 제공
- 지역 사찰의 고유 콘텐츠와 행사 정보를 균형 있게 확산
- 전통공예 작가 및 지역 문화 종사자와의 협업 구조 확장
- 협력 사찰 20~25개소 대상 행사/프로그램 홍보 계약 기반 B2B 수익 창출

## 현재 구현 상태

React와 Vite로 `홈`, `스캔`, `탐색`, `내 정보`(마이페이지) 4개 하단탭을 구현한 모바일 웹
프로토타입입니다. 별도 휴대폰 목업 프레임 없이 브라우저 전체 뷰포트를 앱처럼
사용하며, 화면별 코드는 유지보수를 위해 `src/pages` 아래 폴더로 분리했습니다.

```text
src/pages/home
src/pages/scan
src/pages/search
src/pages/auth
src/pages/mypage
```

### 홈

- Supabase `temples` 데이터를 기반으로 활성 사찰 목록을 읽습니다.
- 브라우저 GPS가 허용되면 현재 위치에서 가까운 사찰을 계산해 추천합니다.
- 이달의 행사는 `/api/monthly-temple-events` 서버 라우트가 TourAPI
  `searchFestival2`를 호출해 가져옵니다.
- 행사 기간이 현재 달과 겹치고 사찰/불교 관련 키워드에 맞는 행사만 노출합니다.
- 행사 좌표와 현재 위치가 모두 있을 때만 자동차 아이콘 옆에 `km` 단위 거리를
  표시합니다. 좌표 또는 현재 위치가 없으면 자동차 아이콘과 거리 줄은 숨깁니다.
- 행사 카드 제목 영역 높이를 고정해 제목이 1줄/2줄이어도 하단 정보가 같은
  위치에 오도록 맞췄습니다.

### 스캔

- 카메라 촬영과 갤러리 업로드 흐름을 모두 지원합니다.
- 분석 전 이미지를 최대 1200px 기준 JPEG로 압축해 API 요청 크기를 줄입니다.
- `/api/recognize-heritage` 서버 라우트가 Supabase의 `heritages`와
  `heritage_images` 후보를 가져와 OpenAI Responses API로 이미지 비교를 수행합니다.
- 기본 모델은 `gpt-5`이며, `OPENAI_RECOGNITION_MODEL` 환경변수로 교체할 수 있습니다.
- 응답은 JSON으로 파싱하고, 일치도가 기준치보다 낮으면 인식 실패로 처리합니다.
- 결과 화면 상단에는 문화재 설명만 표시하고, 모델의 판단 근거 문구는 노출하지 않습니다.
- 촬영/업로드 후 최신 GPS를 받아 가장 가까운 활성 사찰을 찾습니다. 기본 500m 이내일 때만
  해당 `temple_id`의 활성 문화재 전체를 비교합니다. 서버 환경변수
  `RECOGNITION_MAX_TEMPLE_DISTANCE_METERS`로 허용 거리를 변경할 수 있습니다.
- 홈 위치 조회와 공통 `locationService`를 사용하되, 스캔은 5분 캐시 대신 최신 고정밀
  위치를 요청합니다(최대 8초). 위치 오류는 기존 분석 오류 화면에 표시합니다.
- 후보 조회는 `id,name,temple_id`만 사용하며, 참조 사진은 대표 이미지 우선 최대 2장입니다.
  같은 URL은 제거하고 두 번째 사진은 다른 `angle_type`을 우선합니다. 설명/도슨트/상세/스탬프는
  OpenAI 입력에 넣지 않고, 일치 결과가 나온 후 해당 문화재 한 건의 상세·asset만 조회합니다.
- 기존 `RECOGNITION_CANDIDATE_LIMIT`는 더 이상 후보를 잘라내지 않습니다. DB 조회는 페이지로
  끝까지 읽습니다. 사찰당 200건 초과는 `TOO_MANY_CANDIDATES`로 명시적으로 중단하며 임의로
  후보를 제외하지 않습니다. 참조 이미지가 없는 문화재가 하나라도 있으면
  `NO_REFERENCE_IMAGES`로 관리자에게 사진 등록을 안내합니다.
- GPT-5 및 기존 추론 설정, JSON 객체 출력, confidence 기준 0.35를 유지합니다.
  출력 제한은 기본 250토큰이며 `incomplete/max_output_tokens`일 때만 기존 1200토큰으로
  한 번 재시도합니다. 이 제한에는 추론 토큰도 포함되므로 재시도가 많으면 시간이 증가할 수
  있습니다. 잘린 JSON은 인식 성공으로 처리하지 않습니다.
- 이미지는 기존 긴 변 1200px·JPEG 품질 0.82 압축을 유지합니다. 이미 압축 중이므로
  불필요한 재압축이나 해상도 확대를 추가하지 않았습니다.

#### 인식 성능 로그와 오류 구분

Vercel에서 `recognition:request`를 검색하면 요청별 JSON 로그를 확인할 수 있습니다.
`requestId`는 동시 요청을 구분합니다. `timingsMs`의 `bodyParsing`, `nearestTemple`,
`candidates`, `openai`, `detail`은 각 단계의 밀리초이며, 실행하지 않은 단계는 `null`입니다.
`totalMs`는 서버 처리 전체 시간입니다. `templeId`, `distanceMeters`, `candidateCount`,
`referenceImageCount`, `openaiAttempts`, `code`도 기록됩니다. API 키, 원본 좌표, 사진,
base64 및 upstream 오류 본문은 로그에 남기지 않습니다.

같은 사찰/촬영 이미지로 여러 번 실행해 각 단계와 전체 시간의 중앙값을 기존 약 15초와
비교하세요. `openaiAttempts: 2`는 출력 토큰 부족 재시도를 뜻합니다. 브라우저에서 체감하는
총시간에는 서버 로그에 포함되지 않는 GPS 조회·이미지 압축·업로드·결과 렌더링도 있으므로
개발자 도구 Network와 함께 확인해야 합니다. 자동화된 mock 테스트 시간은 실제 GPT 응답
속도의 측정치가 아닙니다.

API의 `code`로 `NO_NEARBY_TEMPLE`, `NO_HERITAGES`, `NO_REFERENCE_IMAGES`,
`NO_MATCH`, `OPENAI_ERROR`, `OPENAI_INCOMPLETE`, `OPENAI_INVALID_OUTPUT`,
`SUPABASE_ERROR` 등을 구분합니다. 사진 불일치는 기존처럼 `ok: true, match: null`이고,
위치/데이터 오류는 `ok: false` 및 사용자 안내 문구를 반환합니다. 클라이언트의
`GPS_PERMISSION_DENIED`, `GPS_LOOKUP_FAILED`, `GPS_UNAVAILABLE`는 요청 전에 처리합니다.

### 검색/도감

- 검색 탭은 사찰, 문화유산, 템플스테이/행사, 테마 투어 카테고리를 보여주는
  프로토타입 화면입니다.
- 지도/스탬프 도감 UI는 Figma 기반 로컬 이미지와 SVG 자산으로 구성했습니다.
- 인식 성공 시 문화유산 ID 기준으로 스탬프를 자동 획득합니다. 비회원 기록은 브라우저에,
  회원 기록은 로그인한 계정의 Supabase `user_stamps`에 저장합니다.
- 도슨트의 더보기와 탐색 화면에서 같은 획득 기록을 확인합니다. 재인식해도
  획득 수와 최초 획득일은 유지됩니다.
- 탐색에서 우표 스탬프/전체 문화유산 도감 전환, 이름·사찰 검색, 상세 정보와
  도슨트 다시 열기를 지원합니다.
- 콘텐츠는 DB의 설명·도슨트 원고, `heritage_assets`의 썸네일/스탬프 이미지,
  선택 `content` 필드에서 불러옵니다.
  이미지와 원고가 없으면 준비 중 상태로 표시합니다.
- [워크플로우와 DB 콘텐츠 등록 형식](docs/heritage-workflow.md)에 콘텐츠 필드를 정리했습니다.

### 회원과 마이페이지

- 하단 탭바는 Figma의 4가지 선택 상태를 적용한 전체 폭 흰색 바입니다. 콘텐츠 높이는 67px이며
  기기의 하단 안전 영역을 추가합니다. `내 정보`는 기존 마이페이지로 연결됩니다.
  Android 시스템 탐색 버튼은 앱 안에 복제하지 않고 기기의 기본 영역을 사용합니다.

- 로그아웃 상태에서 이메일·Google·비회원 시작 화면을 표시합니다. 이미 비회원 시작을
  선택한 기기는 다음 실행 시 바로 앱으로 진입하며, 로그아웃하면 시작 화면으로 돌아갑니다.
- 이메일 가입·인증·로그인·비밀번호 재설정과 Supabase Google OAuth를 연결했습니다.
- 시작 화면의 `이미 회원이신가요? 로그인`과 비회원 마이페이지의 `로그인 연동`은
  이메일 로그인 화면을 바로 엽니다. 같은 화면에서 Google로 로그인할 수 있습니다.
  로그인은 약관 화면을 거치지 않으며, 동의 기록이 없는 기존 회원도 로그인할 수 있습니다.
- 필수 동의 3개(만 14세 이상, 이용약관, 개인정보 수집·이용)를 모두 체크해야
  `동의하고 시작하기`가 초록색으로 활성화됩니다. 전체 동의는 선택 항목도 함께 체크합니다.
  위치기반서비스와 사찰 소식·행사 알림 동의는 선택입니다.
- 회원의 동의 버전과 선택 항목은 `user_consents`에 서버 시각으로 저장합니다.
  필수 동의는 가입 단계에서 받고 로그인 중에는 동의를 요구하거나 동의 기록을 만들어 넣지 않습니다.
  회원 스탬프 저장은 인증된 사용자 ID와 요청 계정의 일치 여부를 DB에서 검사합니다.
- 로그인하면 기존 비회원 스탬프와 스캔 기록을 계정에 병합합니다. 중복 우표는 최초
  획득일을 유지합니다. 서버 저장과 재조회가 성공한 기록만 비회원 저장소에서 제거합니다.
  실패 시 원본을 유지하고 마이페이지·도감에서 다시 시도할 수 있습니다.
- 회원 스탬프를 비회원 저장소에 복사하지 않으며, 계정 변경·로그아웃 시 이전 회원의
  기록을 화면에서 즉시 숨깁니다. 기존 홈·탐색·스캔·도슨트는 양쪽 모드에서 유지합니다.
- 마이페이지는 실제 수집 기록으로 방문 사찰·스캔 유물·수집 우표 수를 계산하고,
  우표 도감, 브라우저 권한 요청, 알림 수신 설정 저장, 로그아웃, 회원 탈퇴를 제공합니다.
  알림 설정은 회원 프로필/비회원 기기에 저장하는 수신 선호이며, 푸시 발송은 아직 없습니다.
- 마이페이지의 위치·카메라 권한은 브라우저의 실제 상태를 조회하고, 권한 변경 및 화면 복귀 때
  갱신합니다. 항목을 누르면 Figma 안내 팝업이 열리고, 허용 버튼을 눌러야 실제 권한을 요청합니다.
  카메라 확인용 트랙은 종료한 뒤 스캔 화면에서 영상 전용 카메라를 켭니다.
  권한 조회 API를 지원하지 않아도 직접 권한을 요청할 수 있습니다.
  차단·HTTPS 필요·카메라 없음·GPS 실패는 화면 안의 안내로 구분합니다.
  브라우저에서 이미 차단한 권한은 사이트 설정에서 사용자가 허용해야 합니다.
- 홈에서 처음 위치 권한을 요청할 때와 스캔에서 카메라를 켜기 전에 같은 안내 팝업을 사용합니다.
  사진 대체 버튼은 사진 선택 후 기존 인식·회원 스탬프 저장으로 이어집니다.
  직접 지역 선택은 GPS를 요청하지 않고 등록된 주소로 사찰을 필터링하며, 선택은 기기에 저장합니다.
  지역 선택을 실제 GPS로 취급하지 않으므로 행사 거리와 스캔의 실제 위치 검증에는 사용하지 않습니다.
- 비회원 초기화와 회원 탈퇴는 화면에서 재확인합니다. 탈퇴 API는 인증 토큰을 검증한
  본인 계정만 삭제하고 회원 데이터는 외래 키로 함께 삭제됩니다.
- 약관 본문은 아직 제공되지 않아 `보기`는 준비 중 안내를 엽니다.

#### 실제 Supabase에 적용할 설정

현재 코드와 SQL은 준비되어 있으며, 원격 DB SQL 적용은 사용자가 직접 진행합니다.

1. 해당 Supabase 프로젝트의 **SQL Editor → New query**에서
   [회원시스템 SQL](supabase/migrations/20261001_member_system.sql) 전체를 실행합니다.
   기존 사찰·문화유산·이미지 테이블은 유지하고 회원 테이블 4개, 프로필 생성 트리거,
   회원별 RLS 정책과 동의/스탬프 저장 RPC를 추가합니다. 기존 `heritages.id`의 타입은 `text`입니다.
   이어서 [로그인 동의 분리 SQL](supabase/migrations/20261001_member_login.sql)을 실행합니다.
   앞선 회원시스템 SQL을 이미 적용했다면 새 SQL만 실행하면 됩니다. 이 변경은 기존 회원이
   동의를 다시 하지 않고 로그인·스탬프 저장을 할 수 있게 하고 계정별 RLS 및 본인 검사도 유지합니다.
2. **Authentication → URL Configuration**에서 **Site URL**은 실제 배포 주소,
   **Redirect URLs**는 앱 루트 주소와 개발 주소(`http://localhost:5173/`)를 등록합니다.
   승인된 HTTPS 테스트 주소가 있다면 그 앱 루트 주소도 등록합니다.
3. **Authentication → Sign In / Providers → Email**에서 이메일 가입을 활성화하고
   이메일 확인 옵션을 유지합니다. 인증/재설정 메일을 운영하려면 SMTP와 발송 제한도 확인합니다.
4. 같은 제공자 설정의 **Google**에서 활성화한 뒤 Google OAuth Client ID와 Client Secret을
   Supabase 대시보드에 입력합니다. Google Cloud의 웹 OAuth 클라이언트에는 앱 origin과
   Supabase Google 제공자 화면의 callback URL을 등록합니다. 이 값들은 `VITE_` 환경변수에 넣지 않습니다.
5. 이메일 가입 → 인증 링크 → 로그인 → 스캔 → 로그아웃 → 재로그인 순으로 확인합니다.
   다른 기기의 같은 계정에서 스탬프를 확인하고, 다른 계정에는 이전 회원 우표가 나타나지 않는지 확인합니다.

Google 로그인은 2026-10-01 원격 조회에서 비활성화 상태였습니다. 설정 전 버튼을 누르면
이메일로 시작하라는 안내가 나오며 앱에서 벗어나지 않습니다.
설정 안내: [Supabase Google 로그인](https://supabase.com/docs/guides/auth/social-login/auth-google),
[로그인 Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).
자동 테스트는 로컬 PostgreSQL 및 모의 Auth/API를 사용하므로 실제 메일 전달·Google 계정
인증·다른 기기 동기화 확인은 위 설정을 적용한 원격 환경에서 진행해야 합니다.

## 데이터 및 API 구조

### Supabase

- 브라우저 클라이언트: `src/lib/supabaseClient.js`
- 브라우저 읽기 서비스:
  - `src/services/templeService.js`
  - `src/services/heritageService.js`
- 서버 관리자 클라이언트: `server/supabaseAdmin.js`
- 주요 테이블:
  - `temples`: 사찰 기본 정보, 좌표, TourAPI content id, 대표 이미지
  - `heritages`: 문화재/인식 대상 기본 정보, 도슨트 텍스트, 사찰 연결
  - `heritage_images`: 문화재별 참조 이미지, 각도, 대표 이미지 여부
  - `heritage_assets`: 문화재별 썸네일 이미지와 스탬프 이미지
  - `profiles`: 회원 이름과 알림 수신 설정 (`auth.users.id`와 연결)
  - `user_consents`: 회원별 동의 버전, 필수·선택 항목, 동의 시각
  - `user_stamps`: 회원별 문화유산 우표와 최초 획득 시각
  - `user_scans`: 회원별 고유 스캔 문화유산과 최초 스캔 시각
- 테스트용 문화재 데이터로 `지갑`, `에어팟`, `노트북`을 넣어 OpenAI 이미지 인식
  흐름을 검증했던 원본은 `tests/fixtures/recognition`에 개발용으로 보관합니다.
  앱에서 import하지 않으며 운영 빌드에 포함되지 않습니다. 원격 DB의 테스트 행은
  이번 코드 정리에서 수정하지 않았으므로 배포 전에 활성 여부를 확인해야 합니다.

### 서버 라우트

- `api/monthly-temple-events.js`: TourAPI 행사 조회, 필터링, 12시간 메모리 캐시
- `api/recognize-heritage.js`: OpenAI 이미지 인식, Supabase 후보 조회, 인식 결과 정규화
- `api/delete-account.js`: Supabase에서 bearer token 검증 후 본인 회원 탈퇴
- `vite.config.js`: 로컬 개발 중에도 Vercel 스타일 `api/` 라우트를 실행하도록
  Vite middleware를 연결합니다.

1. PRD와 발표자료 PDF를 읽고 서비스 개요, 기능 목록, 비즈니스 모델을 README로 정리했습니다.

   기반 사찰 데이터 import 스크립트를 작성했습니다.

9. 인식 결과 화면에서 판단 근거 문구를 제거하고, 사용자에게 필요한 이름/설명/도슨트
   중심으로 표시하도록 다듬었습니다.

## 코드 구성과 정리 기록

- `src/pages/home`, `scan`, `search`: 페이지별 화면과 CSS. 홈의 팝업·슬라이드와
  스캔 이미지 전처리는 해당 기능 폴더 안에 둡니다.
- `src/components`: 앱 프레임, 탭, 공유 스탬프 카드와 컬렉션 상태.
- `src/hooks/useCurrentLocation.js`: 중복 위치 요청 방지와 5분 위치 재사용.
- `src/services`: Supabase, 서버 API, 브라우저 저장소 접근.
- `src/utils`: 좌표·거리 계산, 문화유산 정규화, 읽기 요청 캐시.
- 사찰·도감 조회는 1분, 월별 행사 조회는 5분 동안 재사용합니다. 동시 요청은
  하나로 합치며 오류는 캐시하지 않습니다. 도감의 다시 불러오기는 캐시를 갱신합니다.
- 인식 결과에 DB 콘텐츠가 있으면 문화유산을 다시 조회하지 않습니다. ID 중심의
  이전 응답은 조회 경로를 유지합니다.
- 위치를 사용할 수 없을 때도 DB 사찰을 표시합니다. DB가 비어 있거나 조회에
  실패하면 임의의 사찰명을 채우지 않습니다.
